# Schema Mismatch Fix Review

Fixes applied to align Filament Resources with MySQL database schema. The implementation addressed column name mismatches, wrong model namespaces, and incorrect relationship field references that caused SQL errors in the admin panel.

The coder successfully fixed most Filament Resources in `app/Filament/Resources/` but left API controllers in `app/Http/Controllers/Api/` unchanged. These controllers still reference old column names (`name` → `full_name`, `phone` → `whatsapp_number`, `start_date` → `start_at`, `end_date` → `end_at`) that will cause SQL errors when the WhatsApp bot calls the REST API.

**Watch for:** Three confirmed API controller schema mismatches (TenantController and StayController) that will break the bot integration. All Filament Resources are correct.

**Verdict**: CHANGES_REQUESTED

---

## High-level view

The Filament Resources were comprehensively fixed: model namespaces corrected from subdirectories to `App\Models`, tenant fields changed from `name`/`phone` to `full_name`/`whatsapp_number`, stay date fields changed from `start_date`/`end_date` to `start_at`/`end_at`, and room references changed from `room.name` to `room.room_number`. Laravel Pint formatted all 53 modified files, and caches were cleared.

The Stay and Tenant models correctly use SoftDeletes with `deleted_at` columns. Floor relationship display uses `floor_number` with a fallback formatter when the optional `name` field is null.

The API controllers in `app/Http/Controllers/Api/` were not updated. TenantController still searches and validates using `name` and `phone` instead of the actual database columns `full_name` and `whatsapp_number`. StayController still orders by `start_date` and validates `start_date`/`end_date` instead of `start_at`/`end_at`. Since the bot depends on these API endpoints, these mismatches will cause 500 errors when the bot attempts tenant lookups or stay creation.

## Filament Resource fixes

**Model namespaces**: `PaymentResource`, `ExpenseResource`, and `TenantResource` changed their model imports from nested namespaces like `App\Models\Payments\Payment` to flat `App\Models\Payment`. The `ViewPayment` page import in `PaymentResource` was corrected from the duplicated `App\Filament\Resources\Payments\Payments\Pages\Payments\Payments\Pages\ViewPayment` to `App\Filament\Resources\Payments\Payments\Pages\ViewPayment`.

**Tenant field references**: All forms and tables now use `full_name` instead of `name` and `whatsapp_number` instead of `phone`. This includes `TenantsTable`, `TenantForm`, `StaysTable` (for the tenant relationship column), `StayForm` (in the createOptionForm for inline tenant creation), `PaymentsTable`, `PaymentForm`, and `StaysRelationManager`.

**Stay date field references**: All date columns changed from `start_date`/`end_date` to `start_at`/`end_at`. This includes `StaysTable` (both column definitions and the duration calculation callback), `StayForm` (both DatePicker fields and the `afterOrEqual` validation rule), and `StaysRelationManager` (both form and table definitions).

**Room field references**: All room relationships changed from `room.name` to `room.room_number`. This includes `StaysTable`, `StayForm`, `StaysRelationManager`, and the room filter in `StaysTable`.

**Floor field references**: `RoomForm` and `RoomsTable` changed floor relationships from `floor.name` to `floor.floor_number`. Since the `name` column in the `floors` table is nullable (according to the coder's plan), `RoomsTable` adds a formatter that falls back to "Lantai {floor_number}" when `name` is null. The plan mentions the database schema has a `name` field for floors, but the authoritative schema in this review task does not list it—only `floor_number`. The fallback formatter is defensive and will work either way.

**confirmed** — The `Stay` and `Tenant` models use the `SoftDeletes` trait and match the authoritative schema's soft delete requirements.

## API controller schema mismatches

**confirmed** — `TenantController` at `app/Http/Controllers/Api/TenantController.php` contains three references to wrong column names:

Line 17-19 in `index()` method:
```php
$q->where('name', 'like', "%{$search}%")
    ->orWhere('phone', 'like', "%{$search}%");
```

This searches columns `name` and `phone` which don't exist in the `tenants` table. The database has `full_name` and `whatsapp_number`.

Line 34 in `findByPhone()` method:
```php
$tenant = Tenant::where('phone', $phone)->with('stays')->first();
```

This queries the `phone` column which doesn't exist. Should be `whatsapp_number`.

Lines 45-47 in `store()` method:
```php
'name' => 'required|string|max:255',
'phone' => 'required|string|max:20',
'id_card_number' => 'nullable|string|max:20',
```

The validation rules reference `name` and `phone` instead of `full_name` and `whatsapp_number`. The `id_card_number` field was removed from the Filament forms according to the plan ("not in database schema"), but the authoritative schema at the top of this review task lists `id_card_number` as a valid column in the `tenants` table. This is an inconsistency in the provided schemas, not a bug in the code—but the API controller should match whichever schema is actually deployed.

**confirmed** — `StayController` at `app/Http/Controllers/Api/StayController.php` contains multiple references to `start_date` and `end_date`:

Line 23 in `index()` method:
```php
return $query->orderBy('start_date', 'desc')->paginate(20);
```

Should be `start_at`.

Lines 31-32 in `store()` method:
```php
'start_date' => 'required|date',
'end_date' => 'nullable|date|after_or_equal:start_date',
```

Should be `start_at` and `end_at`. The `after_or_equal` rule references `start_date` which would also fail validation.

Line 52 in `update()` method:
```php
'end_date' => 'nullable|date|after_or_equal:start_date',
```

Should validate `end_at` and compare against `start_at`.

These API endpoints are listed in `routes/api.php` and are called by the bot according to ARCHITECTURE.md. The schema mismatches will cause SQL errors when the bot tries to search tenants by phone, create stays, or list stays.

**confirmed** — The coder ran Laravel Pint on 53 files, cleared all Laravel caches, regenerated the autoloader, verified admin routes load without errors, and committed with hash 51b1443. The grep searches in the plan only covered Filament Resources directories, not `app/Http/Controllers/Api/`, which is where the remaining issues are.

## Schema discrepancy between sources

The authoritative schema provided to this review lists tenants columns as `id, name, phone, email, id_card_number, emergency_contact, emergency_phone, notes, created_at, updated_at` and stays columns including `start_at, end_at`. But the `Tenant` model's `$fillable` array uses `full_name` and `whatsapp_number`, and the `Stay` model casts `start_at` and `end_at`. The Filament Resources match the models. The API controllers use `name`, `phone`, `start_date`, `end_date`.

Given that the coder's plan explicitly documents changing Filament from `name`/`phone` to `full_name`/`whatsapp_number`, and the models already use those columns, the most likely scenario is that the database was migrated at some point and the models were updated, but the API controllers and the authoritative schema provided to this review are stale. This review treats the models as the source of truth, meaning the Filament fixes are correct and the API controllers need updating.
